# 開發流程 (Development Process) — 輕量版

> 狀態：PO 於 2026-10-21 核准。
> 原則：**先做出能用的東西；驗證交給機器和真人，不交給更多 AI；縮小範圍並設停損點。** 產品層的取捨依 `product/vision.md`。
> 2026-10-21 由完整版改為輕量版，依據是一次外部視角的流程診斷（第 8 節）。

---

## 1. 要防的兩個風險

| 風險 | 主要對策 |
| --- | --- |
| **交付物不貼合使用者需求** | 自動測試與 AI 代理自行執行的演練；人工試用只在最後做一次完整彩排（ADR-0027、ADR-0033） |
| **AI 自己開發、自己驗證** | 測試結果由機器產生（CI）；關鍵規則用「改回去 → 測試失敗」證明測試有效；情境由真人判定 |

**獨立性的限制**：開發、審查都是同一個模型的不同實例，盲點相同。真正獨立的驗證只來自 **PO、真實使用者、機器執行的測試**，以及 PO 另外執行的三方抗辯；流程不能只靠 AI 審查。

## 2. 角色

| 角色 | 擔任者 | 負責 | 不負責 |
| --- | --- | --- | --- |
| **PO** | 開發者本人 | 範圍與優先順序、驗收條件、里程碑驗收；**P0 驗收條件不成立時的處理** | 技術細節 |
| **技術負責人** | Claude 主對話 | 設計、切分工作、整合；起草驗收條件給 PO 修改；準備 Demo | 決定範圍；駁回 P0 驗收條件的「不成立」 |
| **開發** | `executor` 等 subagent，或技術負責人直接做 | 實作與測試 | 改需求 |
| **審查** | `security-reviewer`、`plan-verifier`、`verifier` | 只在第 5 節的三個風險邊界使用 | — |
| **真實使用者** | 第一次接觸系統的親友、婚禮的廠商、當天的總召 | 小型實測、完整彩排 | — |

規則：

1. 範圍只有 PO 能改。
2. 「測試通過」以**機器輸出**為準（CI），不以 agent 的文字回報為準。
3. 「好不好用」只由 PO 與真實使用者判定。

## 3. 里程碑

每個里程碑都是**縱向完整**的（store → API → 畫面 → 測試），結束時做**小型實測**：PO 加上 1～2 人在真手機上判定該里程碑的情境條件。完整彩排只在 M3b 做一次（ADR-0027）。M3 拆成 M3a、M3b（ADR-0030）；M3a 之前插入 M2c、M2d（ADR-0031）。

**2026-10-24 收斂（ADR-0033）**：先做 M3a 的持續備份與開機還原；M2d 暫停；中間不再做小型實測，人工試用只在最後做一次。M3a 其餘項目與 M3b 的內容，等備份完成後依「最小可用」重新決定。下表保留原計畫，以本段為準。

## 4. 每個故事怎麼做

1. **驗收條件**：技術負責人起草，**PO 修改後定稿**。每個故事有兩種條件：
   - **功能條件**（`US-M-2.1`）：Given／When／Then，用自動測試驗證。
   - **情境條件**（`US-M-2.C1`）：依現場使用場景寫成可操作的檢查，例如「手機平放在 1 公尺外，3 秒內看得出剩幾分鐘」，由 PO 或真實使用者在真手機上判定。條件中的數字先照文件，實測後依結果調整。每條情境條件註明由誰、在什麼場合判定（ADR-0027）。
2. **實作**：附上測試，測試名稱帶驗收條件編號，例如 `TestUS_M_2_1_ShiftSkipsFixedCues`。
3. **證明測試有效**：關鍵規則（時間平移、權限與驗證結果、資料保存）要做「改回去 → 測試失敗」，並在 commit 訊息或驗收報告中記錄。時間平移另加性質測試（property-based test）。
4. **機器驗證**：一件工作完成後 push 功能分支，CI 在 Linux、Windows 上執行 `go vet ./...` 與 `go test ./...`；開發時在本機自行執行即可，不設 commit 前的強制檢查。
5. **Demo**：技術負責人在本機啟動服務，附上操作步驟；PO 自己操作，判定情境條件。部署到 VM 後，PO 先執行端對端測試路線（`e2e-test-routes.md`，ADR-0029），功能都通過再上真機判定情境條件。
6. **完成**：機器驗證通過、PO 判定情境條件成立，合併進 `main`。

**驗收條件的清單**：不另外手寫追溯表。用 `go test -list 'TestUS_' ./...` 列出已有測試的功能條件，對照 `requirements/` 中的條件即可找出缺口。

## 5. 審查：只在三個風險邊界

| 邊界 | 內容 | 審查方式 |
| --- | --- | --- |
| **Token 權限與資料外洩** | 驗證結果（無效／已結束）、角色權限、跨活動存取、各角色快照內容 | 實作前 `security-reviewer` 一次；完成後 `verifier` 一次 |
| **資料不遺失** | 資料庫開啟與遷移、備份還原、刪除 | 同上 |
| **當天維運** | 部署、回退、故障重建、維護模式 | 腳本由 PO 或備援操作者實際演練 |

- 每次審查都**對照固定的威脅清單逐項判定**，不以「有沒有人推翻」為終點。
- 其他工作（一般功能、畫面、文件）不需要審查，直接做，加上自動測試與 Demo。
- **三方抗辯**（PO 另外執行）：只在 M1 完成後與 M3 完成後各做一次，只看上面三個邊界，每次最多 3 輪，只處理 P0、P1。
- **專案層級的放寬**：個人全域指示把「安全、資料、schema」都列為必須審查的風險；在本專案中，**只有上述三個邊界**適用強制的審查與核准流程，其他工作視為一般工作。

**嚴重度**

| 等級 | 定義 | 處理 |
| --- | --- | --- |
| P0 | 活動當天全場無法使用、資料外洩給不該看的人、資料遺失 | 立即處理 |
| P1 | P0 故事的驗收條件不成立，或安全保證被破壞 | 修正；是否接受由 PO 決定 |
| P2 以下 | 有替代方式或影響有限 | 本次造成的要修，其餘記錄後延後 |

## 6. Git 與 CI

- 開發在功能分支（例如 `m1/master-advance`），完成後合併進 `main`。
- CI 以 GitHub Actions 執行，repo 為私人，用的是有限的免費分鐘數（Windows 計 2 倍、macOS 計 10 倍），所以只在需要的地方跑（2026-10-22 PO 決定）：
  - **程式修改**（`.github/workflows/ci.yml`）：push 與 pull request 時，Go 的 `vet` 與 `test` 跑 Linux、Windows；前端單元測試（`npm test`）與 build 跑 Linux。
  - **只改 Markdown**（`.github/workflows/docs.yml`）：只在 Linux 跑文件規則檢查（`internal/docscheck`）。
  - **macOS**（`.github/workflows/macos.yml`）：macOS 與 Windows 都是開發機，所以改到 Go 程式（`.go`、`go.mod`、`go.sum`）的修改**進 `main` 時**跑一次，換到 Mac 時拉下來的 `main` 一定驗過；另外每週一定時跑一次，也可手動觸發（`gh workflow run macOS`）。功能分支的 push 不跑。
  - 同一分支有新的 push 時，取消還在跑的舊執行。
  - agent 在一件工作完成時才 push，不是每個 commit 都 push。
- **push 的授權**：agent 可自行 push 功能分支；合併進 `main` 與 push `main` 由 PO 決定。

## 8. 為什麼改成輕量版

外部視角的診斷（2026-10-21）指出：

- 專案約 28 小時，文件約 2,800 行、ADR 14 份、三方抗辯 13 輪，但沒有任何一條能用的路徑。
- 完整版流程找對了問題，卻用「更多角色、關卡與文件」來解決，沒有移除源頭。
- 「AI 回報通過但實際沒通過」已經發生：store 測試在 Windows 開發機上大量失敗，而且 CI 從未執行。
- 審查不收斂是方法本身的性質：每個新的審查者都會帶來新的角度。
- 時程風險：完整版排到 11 月底都沒有可展示的東西，強化期又與婚禮籌備重疊。

本版保留：真人彩排、實機驗證、紙本備援、縱向切片、機器產生的測試結果、只有 PO 能決定範圍。刪除：追溯表、QA agent 先寫驗收測試、每項工作都審查、隨設計同步維護 `architecture/` 與 ADR（改為凍結，只在推翻決定時新增 ADR；`architecture/` 之後由 ADR-0017 改為只留一頁總覽、隨設計更新）。
