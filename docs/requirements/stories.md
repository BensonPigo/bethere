# 故事與驗收條件

編號規則：功能條件 `US-x-n.m` 以自動測試驗證；情境條件 `US-x-n.Cm` 由真人在真機上判定，集中在最後一次完整彩排。情境條件後的「（已成立）」表示已在真機判定成立，「（待判定）」表示尚未判定。

角色代號：`M` 總召、`ST` 新秘、`H` 新人、`X` 所有角色、`VL` 領班、`RN` 機動組、`RC` 迎賓、`CA` 禮金、`CO` 婚顧公司成員、`O` 維運（`glossary.md` 第 2 節）。

---

## 總召

### US-M-0 婚前準備（以指令完成）

**身為** 開發者（第一場的活動建立者），**我希望** 用伺服器端指令建立活動、角色與 Rundown 並取得各角色的連結，**以便於** 不必等管理介面就能讓總召與新秘開始使用。

狀態：完成

開發者以指令建立活動；受邀的人以邀請碼在畫面上建立見 US-M-17（ADR-0036）。總召在畫面上的婚前準備見 US-M-10 至 US-M-14。

| 編號 | 驗收條件 |
| --- | --- |
| US-M-0.1 | **Given** 資料庫已初始化，**When** 執行 `bethere create-event`（名稱、日期、時區），**Then** 建立 Draft 活動與唯一的 Master 角色，終端機只顯示一次 Master 連結與復原碼，資料庫只存兩者的雜湊 |
| US-M-0.2 | **Given** 一份 Rundown CSV 檔（格式見下），**When** 以指令匯入，**Then** 建立所有 Cue 與指派；任一列不合法（時間格式、角色不存在、順序重複）時整份不寫入，並列出錯誤列 |
| US-M-0.2a | 匯入只允許在 Draft 階段，且活動中尚無 Cue；要重來就重建活動 |
| US-M-0.3 | **When** 以指令新增角色（例如「新秘」，類型 Stylist），**Then** 終端機只顯示一次該角色的連結 |
| US-M-0.4 | 指令的輸出只到終端機，不寫入任何日誌（`access-control.md` 第 2 節） |
| US-M-0.C1 | 開發者照 README 的步驟，15 分鐘內從空資料庫準備好一場可彩排的活動（待判定；以正式環境的建置方式判定，建立活動的步驟寫進 runbook） |

**Rundown CSV 格式**：UTF-8（可帶 BOM，方便 Excel 存檔），第一列為欄位名稱，每列一個 Cue。

| 欄位 | 必填 | 格式 | 例 |
| --- | --- | --- | --- |
| `seq` | 是 | 正整數，不重複 | `3` |
| `title` | 是 | 文字 | `一進預備` |
| `start` | 是 | `HH:MM`，24 小時制，活動日當天、活動時區 | `11:15` |
| `duration_min` | 是 | 0 以上的整數 | `15` |
| `fixed` | 否 | `Y` 或空白 | `Y` |
| `roles` | 否 | 角色名稱，多個以 `;` 分隔；角色須已建立 | `新秘;攝影A` |
| `role_note` | 否 | 對所有指派角色相同的備註（各角色不同的備註在編輯器中設定） | `新娘房集合` |
| `note` | 否 | 公開備註 | |

**身為** 總召，**我希望** 在平板上一眼看清完整時間軸、目前進行的環節與各角色的就位狀態，**以便於** 不必到處確認進度。

狀態：完成

| 編號 | 驗收條件 |
| --- | --- |
| US-M-1.1 | **Given** Master 連結，**When** 開啟，**Then** 看到全部 Cue，依順序列出有效時間（`HH:MM`）、標題、狀態圖示（`✔` 完成、`▶` 進行中、`○` 待辦、`■` 固定） |
| US-M-1.2 | 目前進行中的 Cue 顯示在右欄最上方，含已進行時間與預計長度（`screen-design.md` 3.1） |
| US-M-1.3 | 時間軸自動捲動到目前的 Cue，下一個 Cue 保持可見 |
| US-M-1.4 | 畫面每 2 秒更新一次；另一台總召裝置的操作在 3 秒內反映（NFR-2） |
| US-M-1.6 | 主控台右欄顯示每個非 Master 角色的就位狀態（`● 已就位` ／ `○ 未就位`，顏色加圖示加文字）與連結最近使用時間（「2 分鐘前」，取自 `lastSeenAt`） |
| US-M-1.7 | 點角色開啟選單：代為打卡／取消打卡、重發連結、撤銷連結 |
| US-M-1.8 | 總召代打卡寫入 `byRoleId` = Master；角色快照的就位狀態同步改變；寫入操作紀錄 |
| US-M-1.9 | 就位打卡與取消（本人或代打）**不改變** `eventVersion`；總召在廠商打卡後立即推進不會收到 409（ADR-0023） |
| US-M-1.C1 | 總召單手拿著 iPad 橫放，在昏暗的室內 3 秒內說出「現在進行到哪個環節、下一個是什麼」（已成立） |
| US-M-1.C1 | 總召在走動中 5 秒內說出「還有誰沒到」（已成立） |
| US-M-1.C2 | 第一次拿到 Master 連結、沒看過系統的人，不經任何說明，5 分鐘內完成「推進（第一次推進即開始活動）→ 復原」（`product/vision.md` V1）（已成立） |

### US-M-2 動態時間修正（平移與預覽試算）

**身為** 總召，**我希望** 某個環節延誤時，用一個大按鈕把後續環節一起往後移，**以便於** 所有人的時間表自動重算，不必逐一通知。

狀態：完成

| 編號 | 驗收條件 |
| --- | --- |
| US-M-2.1 | **Given** 活動為 Live，**When** 總召點「+5」「+10」「−5」或自訂分鐘數，**Then** 開啟預覽面板：起點預設為下一個待辦的 Cue，列出會被移動的 Cue（新舊時間）與固定環節衝突；預覽不寫入任何資料 |
| US-M-2.2 | 預覽中取消勾選某個 Cue，預覽立即重算，該 Cue 不被移動 |
| US-M-2.3 | **When** 確認套用，**Then** 起點之後所有待辦、非固定、未取消勾選的 Cue 的偏移加上平移量；進行中、已完成、已略過、固定的 Cue 不動；單一交易，`eventVersion` + 1 |
| US-M-2.4 | 負值平移：平移前就已逾時的 Cue 自動排除並在預覽中標示；其餘若有任何 Cue 會早於現在，預覽標紅、停用確認並說明是哪個 Cue；直接呼叫 API 同樣被拒絕 |
| US-M-2.5 | 平移後若某 Cue 的預計結束晚於其後最近的固定環節，**不阻擋**，在預覽與時間軸上標示衝突（`screen-design.md` 3.4） |
| US-M-2.6 | 平移量為 0 或超過 ±1440 分鐘時拒絕 |
| US-M-2.7 | 平移同樣檢查版本：另一台總召裝置先操作過時，套用被拒絕並顯示「畫面已更新，請重新確認」（`sync-and-offline.md` 第 3 節） |
| US-M-2.8 | 每次平移寫入操作紀錄：每個被改到的 Cue 的前後狀態，以及總召的要求（起點、平移量、取消勾選的 Cue） |
| US-M-2.9 | 時間軸上被平移過的 Cue 顯示新時間，旁邊小字顯示原時間，例如 `11:25 原 11:15`（ADR-0028） |
| US-M-2.C1 | 第一次拿到 Master 連結、沒看過系統的人，不經說明，5 分鐘內完成「推進 → 延後 10 分 → 復原」（延續 US-M-1.C2）（已成立） |
| US-M-2.C2 | 總召單手拿 iPad，在走動中 10 秒內完成「+10 → 看預覽 → 確認」（已成立） |

### US-M-3 推進流程

**身為** 總召，**我希望** 在環節轉換時按一個大按鈕推進狀態，**以便於** 系統高亮目前進度並即時讓相關的人知道。

狀態：完成

活動日當天第一次按「推進」就開始活動，沒有獨立的「開始活動」按鈕（ADR-0020）。

| 編號 | 驗收條件 |
| --- | --- |
| US-M-3.2 | **Given** 活動為 Live，**When** 按「推進」，**Then** 目前進行中的 Cue 變為完成（記錄實際結束時間），下一個待辦的 Cue 變為進行中（記錄實際開始時間）；同一時間只有一個進行中的 Cue |
| US-M-3.3 | 推進不需要二次確認；按下後按鈕停用約 1 秒，防止連點 |
| US-M-3.4 | **Given** 兩台總召裝置，**When** A 推進後、B 的畫面尚未更新就按推進，**Then** B 的操作被拒絕，畫面顯示「畫面已更新，請重新確認」並自動刷新（`sync-and-offline.md` 第 3 節） |
| US-M-3.5 | 每次推進都寫入操作紀錄（誰、何時、改了哪些 Cue） |
| US-M-3.6 | **Given** 活動為 Draft 且今天是活動日（依活動時區），**When** 總召按「推進」，**Then** 同一筆交易內活動變為 Live、第一個待辦的 Cue 變為進行中，操作紀錄記下活動開始與這次推進 |
| US-M-3.7 | 非活動日時推進按鈕停用並說明「活動日當天才能開始」；直接呼叫 API 回 `not_event_day` |
| US-M-3.8 | 復原這次推進時，Cue 回到待辦，活動仍維持 Live |
| US-M-3.9 | `POST /api/event/start` 移除（回 404 或 405）；主控台與 Rundown 編輯器都沒有「開始活動」按鈕 |
| US-M-3.C1 | 總召單手拇指在 iPad 上一次點擊完成推進，不會誤觸其他按鈕（已成立） |

### US-M-4 復原上一步

**身為** 總召，**我希望** 誤按推進或平移、略過時能一鍵復原，**以便於** 推進不需要二次確認也不怕按錯。

狀態：完成

| 編號 | 驗收條件 |
| --- | --- |
| US-M-4.1 | **Given** 最近一次 Cue 操作是推進，**When** 按「復原上一步」，**Then** 受影響的 Cue 回到推進前的狀態（進行中 → 待辦、完成 → 進行中），實際時間一併還原 |
| US-M-4.2 | 復原按鈕顯示將被復原的操作（例如「撤銷：推進『一進預備』」） |
| US-M-4.3 | 只能復原最近一次 Cue 操作，而且只能復原一次；沒有可復原的操作時按鈕停用（`data-model.md` 4.1） |
| US-M-4.4 | 復原同樣檢查版本（`sync-and-offline.md` 第 3 節），並寫入操作紀錄 |
| US-M-4.5 | 復原後，新秘的倒數在 3 秒內跟著改變 |
| US-M-4.6 | **Given** 最近一次 Cue 操作是平移，**When** 按「復原上一步」，**Then** 每個被移動的 Cue 精確回到平移前的偏移；復原按鈕顯示「撤銷：+10 分，影響 N 個環節」 |
| US-M-4.7 | 平移與復原的組合以性質測試驗證：任意 Rundown 與任意合法平移，套用後再復原，所有 Cue 與平移前完全相同（NFR-7） |
| US-M-4.8 | 平移後若有 Cue 已被推進（不再是平移後的狀態），復原平移被拒絕並說明原因（ADR-0015） |
| US-M-4.C1 | 總召誤按推進後，5 秒內自己找到並完成復原，不需要別人說明（待判定） |

### US-M-5 超時提示

**身為** 總召，**我希望** 環節拖太久時系統提醒我，並幫我算好要延後多少，**以便於** 我在忙亂中不會忘了通知大家。

狀態：完成

| 編號 | 驗收條件 |
| --- | --- |
| US-M-5.1 | 超時分鐘 = 現在 − 下一個待辦 Cue 的有效開始時間（小於 0 視為 0），由伺服器在 Master 快照中算好（`data-model.md` 4.3） |
| US-M-5.2 | 超時達 5 分鐘時，主控台在目前環節下方顯示「已超時 N 分，要延後後續嗎？」；未滿 5 分鐘不顯示 |
| US-M-5.3 | 點提示開啟平移預覽，起點為下一個待辦的 Cue，平移量預填為超時分鐘以 5 為單位無條件進位（超時 7 分 → +10） |
| US-M-5.4 | 套用平移後超時歸零，提示在下一次更新時消失；系統不會自動平移 |
| US-M-5.C1 | 故意讓一個環節拖 8 分鐘，總召看到提示後 15 秒內完成延後（已成立） |

### US-M-6 略過 Cue

**身為** 總召，**我希望** 取消的環節可以略過，**以便於** 推進時不必經過它，而且仍留下紀錄。

狀態：完成

| 編號 | 驗收條件 |
| --- | --- |
| US-M-6.1 | **Given** 活動為 Live、某 Cue 為 Pending，**When** 總召在 Cue 詳情點「略過」，**Then** 該 Cue 變為 Skipped，`eventVersion` + 1，寫入 `cue.skip` 操作紀錄 |
| US-M-6.2 | 推進跳過 Skipped 的 Cue，直接開始下一個 Pending |
| US-M-6.3 | 進行中、已完成、已略過的 Cue 不能略過（422）；Draft 與 Live 都可以略過，讓活動日當天第一次推進前就能取消環節 |
| US-M-6.4 | 「復原上一步」可撤銷略過，Cue 回到 Pending；復原按鈕顯示「撤銷：略過『…』」；Draft 階段同樣可以復原 |
| US-M-6.5 | 被略過的 Cue 從角色的「下一個與你有關的 Cue」與新秘倒數中消失；時間軸上以 `⊘` 淡化顯示 |
| US-M-6.6 | 略過帶版本號；版本不符時被拒絕（同 US-M-2.7） |

### US-M-7 撤銷與重發角色連結

**身為** 總召，**我希望** 連結外流或對方換了人時，當場讓舊連結失效並拿到新連結，**以便於** 不必找開發者。

狀態：完成

撤銷與重發放在主控台的角色選單，二次確認後顯示新連結與「複製」，新連結由總召自己用 LINE 傳，系統不代發。

| 編號 | 驗收條件 |
| --- | --- |
| US-M-7.1 | **When** 總召對某角色按「重發」並二次確認，**Then** 舊 Token 撤銷、建立新 Token，在同一交易內完成；回應只這一次帶新連結明文，畫面顯示新連結與「複製」按鈕 |
| US-M-7.2 | **When** 按「撤銷」並二次確認，**Then** 該角色沒有任何有效 Token；之後可再「重發」 |
| US-M-7.3 | 持舊連結的裝置在下一次輪詢收到 `invalid`，清除本機快照並顯示「連結已失效，請向總召索取新連結」 |
| US-M-7.4 | 不能對 Master 角色撤銷或重發（Master 只能以復原碼換發）；非 Master 呼叫一律 403 |
| US-M-7.5 | 目標角色屬於別的活動時回 404，不帶 `result`（同 `api.md` 第 6 節「帶 id 的請求」） |
| US-M-7.6 | 撤銷與重發都寫入操作紀錄（誰、何時、對哪個角色），不記錄 Token 或其雜湊；不改變 `eventVersion` 以外的 Cue 狀態，也不是「復原上一步」的步驟 |
| US-M-7.7 | 二次確認的文字說明「舊連結將立即失效，對方需要新連結」 |
| US-M-7.C1 | 總召在 iPad 上 30 秒內完成「重發 → 複製 → 貼到 LINE 傳出」（已成立） |

### US-M-8 活動中新增 Cue 與改派角色

**身為** 總召，**我希望** 現場臨時加的環節能指派給相關的人，**以便於** 他們不必靠口頭通知（ADR-0021）。

狀態：完成

| 編號 | 驗收條件 |
| --- | --- |
| US-M-8.1 | **Given** 活動為 Draft 或 Live（活動日當天第一次推進前仍是 Draft），**When** 總召輸入開始時間、長度、標題，選擇插在哪個 Cue 之後並確認，**Then** 新 Cue 的 `scheduledStart` = 輸入時間、`offsetMin = 0`、狀態 Pending；插入位置之後的 `seq` 依序加一，維持唯一、連續；單一交易，`eventVersion` + 1 |
| US-M-8.2 | 新增時可同時指派角色與角色備註 |
| US-M-8.3 | **Given** Cue 為 Pending，**When** 總召新增或移除指派，**Then** 立即生效；進行中、已完成、已略過的 Cue 不能改指派（422） |
| US-M-8.4 | 新增與改派寫入操作紀錄（`rundown.insert`、`rundown.assign`），**不是**「復原上一步」的步驟；插入 Cue 後，之前的平移仍可復原（ADR-0021「之後要注意」） |
| US-M-8.5 | 新增與改派帶版本號；版本不符時被拒絕 |
| US-M-8.6 | 任一 Pending Cue 的 `effectiveStart` 早於 `seq` 在它前面最近一個未略過 Cue 時，主控台在該 Cue 旁顯示 `⚠`「時間早於前一個環節 HH:MM」，不阻擋（`data-model.md` 4.2 第 5 步） |
| US-M-8.7 | Live 階段可改既有 Cue 的標題與公開備註；不能改既有 Cue 的 `scheduledStart`、長度、固定（`access-control.md` 第 4 節） |
| US-M-8.C1 | 總召在 iPad 上 30 秒內新增「長輩致詞」並指派給音控（已成立） |

### US-M-9 維護中橫幅

**身為** 總召，**我希望** 維護模式下看到明顯的提示，**以便於** 知道其他人此時連不上，要先核對資料。

狀態：完成

| 編號 | 驗收條件 |
| --- | --- |
| US-M-9.1 | 維護旗標為 true 時，主控台頂端顯示醒目橫幅「維護中，其他角色無法連線」，蓋不掉、不能關閉 |

### US-M-10 Rundown 編輯器（Draft）
