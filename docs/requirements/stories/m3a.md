# M3a 資料與維運：故事與驗收條件

> 狀態：**US-O-1 完成**（2026-10-24 在正式專案啟用，雲端演練通過 US-O-1.C1、US-O-1.C2）；其餘故事為**草稿**，依 ADR-0033 在「最小可用」重新決定時定稿或移除。

## 1. 我對需求的理解（請先檢查這段）

- M3a 沒有新的畫面功能給現場的人用，除了兩個小畫面：總召的「維護中」橫幅，以及備援操作者用的 `/recover` 頁面。其餘都在伺服器和腳本。
- **備份**：資料庫每一次寫入，幾秒內就複製到 GCS。VM 或磁碟壞掉時，在新磁碟上開機會自動從 GCS 還原；還原失敗就**不啟動**，絕不開一個空的資料庫，否則所有裝置會收到「連結無效」而清掉離線快取（ADR-0012）。
- **維護模式**：還原完成後，服務先以維護模式啟動。此時只有總召連得上，其他人看到「離線中」並保留快照。總召核對資料沒問題後，備援操作者才解除維護。
- **復原碼**：總召的連結弄丟或外流時，備援操作者在 `/recover` 輸入復原碼，換發一條新的總召連結，再用 LINE 傳給總召；舊連結立即失效。復原碼外流時，由開發者在伺服器上重設。
- **每日刪除**：活動結束（隔天 04:00）後 80 天，伺服器自動刪除整場活動；加上備份最多保留 72 小時，所有副本在 90 天內消失（NFR-5）。
- **演練**：在另一個暫存 GCP 專案用同一套腳本走一次故障重建，不碰正式專案。備援操作者還沒決定，先用 PO 的帳號；人選決定後由他本人再演練一次（ADR-0030）。
- **監控**：伺服器掛掉時，開發者會收到 email；凍結期改通知備援操作者，那一步在婚禮前才切換。

## US-O-1 持續備份與開機還原

**身為** 維運，**我希望** 資料庫持續備份到 GCS，換一顆空磁碟開機也會自動還原，**以便於** VM 或磁碟壞掉時，最多只遺失故障前 10 秒內的操作。

| 編號 | 驗收條件 |
| --- | --- |
| US-O-1.1 | 服務以 `litestream replicate -exec "bethere serve …"` 啟動；Litestream 的版本鎖定，與 Caddy 一樣上傳到發行版 bucket，恢復時不依賴 GitHub |
| US-O-1.2 | 準備腳本：資料庫檔不存在時，先刪除殘留的 `-wal`／`-shm`，再執行 `litestream restore -if-replica-exists`；還原失敗就不啟動 |
| US-O-1.3 | 還原「成功但沒有副本」時，`bethere serve` 因找不到資料庫而拒絕啟動（`tech-stack.md` 2.1「不自動建庫」），不產生空資料庫 |
| US-O-1.4 | 備份 bucket 在同區域，關閉 soft delete、不開物件版本控制、不設生命週期規則；VM 服務帳號對它可讀寫，對發行版 bucket 只能讀 |
| US-O-1.5 | Litestream 快照間隔 24 小時、保留 72 小時；設定寫進發行版與 `tech-stack.md` |
| US-O-1.6 | 只備份正式資料庫；`/var/lib/bethere-e2e` 不備份（ADR-0029） |
| US-O-1.7 | 建立資料庫的使用者、`bethere` 服務與 Litestream 是同一個使用者，資料庫檔權限為 0600；第一次部署的順序確保 Litestream 不會先建出空檔，讓 `BETHERE_INIT` 拒絕 |
| US-O-1.C1 | 演練：以 Master 連結推進一次，10 秒內停掉 VM，依故障重建程序還原，這次推進仍在（NFR-9） |
| US-O-1.C2 | 演練：空磁碟加上錯誤的 bucket 名稱，或拿掉服務帳號的權限 → 服務不啟動 |

## US-O-2 維護模式

**身為** 維運，**我希望** 還原後的服務先只讓總召連線，**以便於** 總召核對資料無誤後，才讓全場看到。

| 編號 | 驗收條件 |
| --- | --- |
| US-O-2.1 | 服務每次啟動前讀取 VM metadata `bethere-maintenance`；鍵不存在視為 0；讀取失敗就**拒絕啟動**，不預設為開放 |
| US-O-2.2 | 維護模式下，`/api/` 只放行 Master Token 的請求，以及復原碼的「換發 Master」；其他 `/api/` 請求回伺服器錯誤（客戶端視為離線、保留快照），不回 `invalid` 或 `ended` |
| US-O-2.3 | 維護模式下，`/healthz` 與靜態檔照常回應 |
| US-O-2.4 | 維護模式下，`lastSeenAt` 只在通過維護檢查之後才更新；被擋下的請求不更新（`api.md` 第 7 節第 5 點） |
| US-O-2.5 | Master 的快照帶維護旗標；非維護時不帶，或為 false（鍵集合以測試固定） |
| US-O-2.6 | 開啟與解除用同一個機制：改 metadata 後重啟服務；有腳本可一行切換並重啟 |
| US-O-2.C1 | 演練：開啟維護模式後，總召的 iPad 看得到資料並顯示橫幅，另一支手機的新秘畫面顯示「離線中」並保留時程；解除後新秘自動恢復，不需要重新整理 |

## US-M-9 維護中橫幅

**身為** 總召，**我希望** 維護模式下看到明顯的提示，**以便於** 知道其他人此時連不上，要先核對資料。

| 編號 | 驗收條件 |
| --- | --- |
| US-M-9.1 | 維護旗標為 true 時，主控台頂端顯示醒目橫幅「維護中，其他角色無法連線」，蓋不掉、不能關閉 |
| US-M-9.2 | 維護模式下總召照常操作（推進、平移、補登等） |

## US-O-3 以復原碼換發 Master 連結

**身為** 備援操作者，**我希望** 總召的連結弄丟或外流時，用復原碼換一條新的，**以便於** 總召不必找開發者就能繼續指揮。

| 編號 | 驗收條件 |
| --- | --- |
| US-O-3.1 | `/recover` 頁面不需要、也不讀取 Token；輸入復原碼後按「換發總召連結」 |
| US-O-3.2 | 復原碼只放在 POST 本文；比對時忽略空白、連字號與大小寫；回應 `no-store` |
| US-O-3.3 | 符合時，在單一交易內撤銷舊的 Master Token、建立新的，並寫入操作紀錄（actor = 復原碼，不記錄任何 Token 或復原碼）；新連結只顯示這一次，以文字加「複製」按鈕呈現，不做成可點的連結 |
| US-O-3.4 | 不符時回「復原碼不正確」，不透露活動是否存在；資料庫錯誤回伺服器錯誤，不回「不正確」 |
| US-O-3.5 | 活動已結束時不能換發 |
| US-O-3.6 | 舊 Master 連結的裝置在下一次輪詢收到 `invalid`，依 `access-control.md` 3.3 處理 |
| US-O-3.7 | 換發後，畫面提醒「若是外流，請總召到角色清單檢查並重發可疑的連結」 |
| US-O-3.C1 | PO 在真手機上：Safari 開 `/recover` → 輸入紙本上的復原碼 → 複製 → LINE 傳出，60 秒內完成；舊連結的 iPad 隨即顯示「連結已失效」 |

## US-O-4 重設復原碼

**身為** 開發者，**我希望** 復原碼外流時能在伺服器上重設，**以便於** 外流的復原碼立即失效。

| 編號 | 驗收條件 |
| --- | --- |
| US-O-4.1 | `bethere reset-recovery-code` 以 Master 連結（從標準輸入讀取，不在命令列參數）指定活動，產生新的復原碼，只印到終端機一次，不寫入日誌 |
| US-O-4.2 | 舊復原碼立即失效；寫入操作紀錄，不記錄任何一個復原碼或其雜湊 |
| US-O-4.3 | 不建立新資料庫；活動已結束時拒絕 |

## US-O-5 每日刪除

**身為** 維運，**我希望** 結束 80 天後的活動自動刪除，**以便於** 兌現「伺服器端所有副本 90 天內消失」（NFR-5）。

| 編號 | 驗收條件 |
| --- | --- |
| US-O-5.1 | 服務內的每日排程刪除 `endsAt` 已超過 80 天的活動，連同角色、Token、Cue、指派、打卡、操作紀錄（外鍵 `ON DELETE CASCADE`） |
| US-O-5.2 | 第 79 天的活動不刪；第 80 天之後的刪除；未結束的活動永遠不刪（以注入的時鐘測試邊界） |
| US-O-5.3 | 刪除失敗只記錄日誌、下次再試，不影響服務；日誌只記活動 id 與筆數，不記名稱或內容 |
| US-O-5.4 | 應用程式不自行執行 checkpoint，交給 Litestream（`tech-stack.md` 2.1「資料刪除」） |
| US-O-5.C1 | 演練：刪除後，以字串搜尋確認活動名稱已不在資料庫檔與 WAL 檔中（RISK-12） |

## US-O-6 當天維運腳本與演練

**身為** 備援操作者，**我希望** 照著腳本處理退版與故障重建，**以便於** 不懂這套系統也能在 15 分鐘內恢復（NFR-8）。

| 編號 | 驗收條件 |
| --- | --- |
| US-O-6.1 | 退版：`ops/gcp/deploy.sh <上一版>`（已存在），手冊寫明如何查上一版的版本號 |
| US-O-6.2 | 故障重建腳本：刪除舊 VM（保留舊磁碟）→ 確認一台都不剩 → 在 `asia-east1` 任一可用區建立恰好一台新 VM（新空磁碟、沿用靜態 IP、目前版本號、`bethere-maintenance=1`）→ 檢查點（恰好 1 台、新磁碟、`/healthz`、HTTPS 憑證）；可用區與版本號為參數 |
| US-O-6.3 | 腳本以 `env.sh` 的專案參數執行，可指向暫存專案；演練不碰正式專案 |
| US-O-6.4 | 紙本手冊（`operations/runbook.md` 第 2 節定稿）：啟動門檻、放棄條件、每一步的指令，可直接印出 |
| US-O-6.C1 | 演練（暫存專案，PO 帳號）：從停掉 VM 到總召核對完、解除維護，15 分鐘內完成（NFR-8） |
| US-O-6.C2 | 演練：完整走一次「故障重建 → 解除維護 → 退版」，全程恰好 1 台 VM，退版後確實是上一版 |
| US-O-6.C3 | 演練：一般重開機後服務自行起來；拿掉發行版 bucket 讀取權後重開，版本相同時仍能啟動 |

## US-O-7 外部監控與告警

**身為** 開發者，**我希望** 伺服器掛掉時收到通知，**以便於** 不必等現場的人打電話才知道。

| 編號 | 驗收條件 |
| --- | --- |
| US-O-7.1 | Cloud Monitoring Uptime Check 從外部探測 `/healthz`，連續失敗時以 email 通知開發者；不在 VM 安裝代理程式 |
| US-O-7.2 | 設定以腳本建立（`ops/gcp/`），可重複執行 |
| US-O-7.3 | 先以小型實驗確認 Litestream 能否提供「尚未複製的變動」；能就加 `/healthz/replica` 與第二個探測，不能就記下結果，改以「活動前一天實際還原一次」為唯一檢查（ADR-0024） |
| US-O-7.C1 | 演練：停掉服務，數分鐘內收到告警 email；恢復後收到恢復通知 |

## 技術工作

| 工作 | 內容 | 依據 |
| --- | --- | --- |
| 選定 Litestream 版本 | 選版本、確認設定格式與 `-if-replica-exists`、`-exec` 的行為；鎖定並寫入 `tech-stack.md` | `tech-stack.md` 2.1「資料刪除」 |
| 新的 API | 復原碼換發 Master；維護模式的中介層；快照加維護旗標；寫入 `api.md` | 本文件 |
| 暫存專案 | 另開一個 GCP 專案、bucket、子網域，演練後刪除 | `operations/runbook.md` 第 2 節 |
| 遷移 | 預計不需要：刪除靠既有的 `ON DELETE CASCADE`；若需要，依 ADR-0019 只新增 | ADR-0019 |

**需要審查的部分**（`process/development-process.md` 第 5 節）：三個風險邊界都涉及。

- **資料不遺失**：備份與還原、不建空庫、每日刪除的邊界。
- **當天維運**：維護模式、故障重建腳本、告警。
- **Token 權限與資料外洩**：復原碼入口、重設復原碼、維護模式的放行規則。
- 實作前、完成後各一次獨立審查；腳本與演練結果另行抗辯（`operations/runbook.md` 第 2 節）。
