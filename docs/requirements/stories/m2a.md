## 1. 我對需求的理解（請先檢查這段）

- M2a 要證明的是第二個核心價值：**總召平移一次，所有相關的人不必被通知就看到新時間**。M1 已證明「推進」這條路是通的，M2a 把「延後」接上，並第一次讓真人在真手機上一起驗證。
- 總召平移前一定先看預覽：會動到哪些環節、會不會撞到固定環節；可以取消勾選某些環節。推進不需要預覽，平移需要，因為平移一次改很多環節而且所有人都看得到。
- 新秘只有在**自己的環節**被移動時才看到「時程已更新」橫幅；別人的環節被移動時不打擾她。（`screen-design.md` 4.4 沒有寫明，這是我的提議，請確認。）
- 新人只看兩樣東西：「一切順利」或「延誤 N 分」，以及目前環節的名稱。延誤包含「總召還沒來得及平移的超時」，未滿 5 分鐘一律顯示「一切順利」。
- 總召不再有「開始活動」按鈕；活動日當天按第一次「推進」就開始。
- 「略過」（`access-control.md` 第 4 節）不在 M2a；第一次彩排的 Rundown 不需要略過環節。（請確認；若要放進 M2a，追加為 US-M-6。）

## US-M-2 動態時間修正（平移與預覽試算）

**身為** 總召，**我希望** 某個環節延誤時，用一個大按鈕把後續環節一起往後移，**以便於** 所有人的時間表自動重算，不必逐一通知。

| 編號 | 驗收條件 |
| --- | --- |
| US-M-2.1 | **Given** 活動為 Live，**When** 總召點「+5」「+10」「−5」或自訂分鐘數，**Then** 開啟預覽面板：起點預設為下一個待辦的 Cue，列出會被移動的 Cue（新舊時間）與固定環節衝突；預覽不寫入任何資料 |
| US-M-2.2 | 預覽中取消勾選某個 Cue，預覽立即重算，該 Cue 不被移動 |
| US-M-2.3 | **When** 確認套用，**Then** 起點之後所有待辦、非固定、未取消勾選的 Cue 的偏移加上平移量；進行中、已完成、已略過、固定的 Cue 不動；單一交易，`eventVersion` + 1 |
| US-M-2.4 | 負值平移：平移前就已逾時的 Cue 自動排除並在預覽中標示；其餘若有任何 Cue 會早於現在，預覽標紅、停用確認並說明是哪個 Cue；直接呼叫 API 同樣被拒絕 |
| US-M-2.5 | 平移後若某 Cue 的預計結束晚於其後最近的固定環節，**不阻擋**，在預覽與時間軸上標示衝突（`screen-design.md` 3.4） |
| US-M-2.6 | 平移量為 0 或超過 ±1440 分鐘時拒絕 |
| US-M-2.7 | 平移同樣檢查版本：另一台總召裝置先操作過時，套用被拒絕並顯示「畫面已更新，請重新確認」（`sync-and-offline.md` 第 3 節） |
| US-M-2.8 | 每次平移寫入操作紀錄：每個被改到的 Cue 的前後狀態，以及總召的要求（起點、平移量、取消勾選的 Cue） |
| US-M-2.9 | 時間軸上被平移過的 Cue 同時顯示新時間與偏移，例如 `11:25（+10）` |
| US-M-2.C1 | 第一次拿到 Master 連結、沒看過系統的人，不經說明，5 分鐘內完成「推進 → 延後 10 分 → 復原」（延續 US-M-1.C2） |
| US-M-2.C2 | 總召單手拿 iPad，在走動中 10 秒內完成「+10 → 看預覽 → 確認」 |

## US-M-4 復原上一步（M2a 追加）

| 編號 | 驗收條件 |
| --- | --- |
| US-M-4.6 | **Given** 最近一次 Cue 操作是平移，**When** 按「復原上一步」，**Then** 每個被移動的 Cue 精確回到平移前的偏移；復原按鈕顯示「撤銷：+10 分，影響 N 個環節」 |

## US-M-5 超時提示

**身為** 總召，**我希望** 環節拖太久時系統提醒我，並幫我算好要延後多少，**以便於** 我在忙亂中不會忘了通知大家。

| 編號 | 驗收條件 |
| --- | --- |
| US-M-5.1 | 超時分鐘 = 現在 − 下一個待辦 Cue 的有效開始時間（小於 0 視為 0），由伺服器在 Master 快照中算好（`data-model.md` 4.3） |
| US-M-5.2 | 超時達 5 分鐘時，主控台在目前環節下方顯示「已超時 N 分，要延後後續嗎？」；未滿 5 分鐘不顯示 |
| US-M-5.3 | 點提示開啟平移預覽，起點為下一個待辦的 Cue，平移量預填為超時分鐘以 5 為單位無條件進位（超時 7 分 → +10） |
| US-M-5.4 | 套用平移後超時歸零，提示在下一次更新時消失；系統不會自動平移 |
| US-M-5.C1 | 彩排中故意讓一個環節拖 8 分鐘，總召看到提示後 15 秒內完成延後 |

## US-ST-2 被動感知時程變更

**身為** 新秘，**我希望** 總召平移時程時，我的畫面自己變化，**以便於** 不必有人跑進新娘房敲門通知。

| 編號 | 驗收條件 |
| --- | --- |
| US-ST-2.1 | 總召套用平移後，新秘的倒數在 3 秒內改為新時間（NFR-2），背景色依新的剩餘時間重新判斷 |
| US-ST-2.2 | 新秘自己的 Cue 被移動時，畫面出現橫幅「時程已更新 +10 分（原 11:15 → 現 11:25）」，倒數區閃爍高亮約 3 秒後收起 |
| US-ST-2.3 | 新秘的 Cue 都沒有被移動時，不出現橫幅 |
| US-ST-2.4 | 同一次平移的橫幅只出現一次；重新整理頁面不會再出現 |
| US-ST-2.5 | 提早（負值）的橫幅用不同顏色與箭頭方向，與延後區分 |
| US-ST-2.6 | 被移動的 Cue 旁保留小字 `（+10）` |
| US-ST-2.7 | 復原平移時同樣出現橫幅（例如「時程已更新 −10 分」） |
| US-ST-2.C1 | 手機平放在化妝台、新秘不碰手機，總召延後 10 分後，新秘在下一次抬頭時說得出「多了 10 分鐘」 |

## US-X-2 活動前看到自己的環節

**身為** 廠商，**我希望** 婚禮前點開連結就看到自己當天的工作，**以便於** 事先確認、當天不慌。

| 編號 | 驗收條件 |
| --- | --- |
| US-X-2.1 | **Given** 活動日以前、活動為 Draft，**When** 角色開啟連結，**Then** 看到指派給自己的 Cue 清單、表定時間與自己的備註，不顯示倒數；頂部窄條為「活動尚未開始（M/D）」 |
| US-X-2.2 | 回應內容與 Live 時相同，只含指派給自己的 Cue（伺服器端過濾，ADR-0007），所以裝置在活動前就存好離線快照 |

## US-X-3 LINE 內建瀏覽器中完整可用

**身為** 從 LINE 點開連結的人，**我希望** 不必改用其他瀏覽器就能使用，**以便於** 不改變我的習慣（V2）。

| 編號 | 驗收條件 |
| --- | --- |
| US-X-3.1 | User-Agent 含 `Line/` 時，只顯示一行非強制的小字「斷網時可能打不開，可改用 Safari／Chrome 開啟」，不阻擋、不跳轉 |
| US-X-3.C1 | 在 iPhone 的 LINE 內建瀏覽器中（預設設定），新秘模式與主控台的全部 M2a 功能在連線時都能使用 |

## US-H-1 新人平安儀表板

**身為** 新人，**我希望** 想看時瞄一眼就知道一切順利，**以便於** 不用為時程操心，也不被任何細節打擾（V3）。

| 編號 | 驗收條件 |
| --- | --- |
| US-H-1.1 | 開啟新人（Host）連結即顯示儀表板，畫面只有兩樣：狀態（「一切順利」或「延誤 N 分」）與目前環節的名稱 |
| US-H-1.2 | 延誤 = 目前（或下一個待辦）Cue 的偏移 + 超時分鐘；未滿 5 分鐘顯示「一切順利」（`data-model.md` 4.3） |
| US-H-1.3 | 新人的回應不含 Cue 清單、備註、角色清單；只有狀態所需的數值與目前環節名稱。回應的鍵集合以測試固定 |
| US-H-1.4 | 畫面沒有任何按鈕；不震動、不發通知、不播放聲音 |
| US-H-1.5 | 總召平移或推進後 3 秒內，儀表板跟著更新 |
| US-H-1.6 | 活動尚未開始時顯示「活動尚未開始」；活動結束與連結失效的處理同其他角色（US-X-1） |
| US-H-1.C1 | 新人穿著禮服、手機拿在手上，2 秒內說出「順利」或「延誤幾分」 |

## 技術工作

不是使用者故事，但必須在 M2a 完成；以測試驗證。

| 工作 | 內容 | 依據 |
| --- | --- | --- |
| 修正 `guardAs` 的檢查順序 | 先確認操作者與目標是同一活動，再判斷活動是否結束；屬於別的活動的 id 回 404、不帶 `result`。以「已結束的別場活動的 id」測試 | `api.md` 第 6 節 |
| 移除 `roles.type` 的 CHECK | 以新增的遷移檔重建 `roles` 表，角色類型改在 Go 驗證；舊版程式能打開新資料庫（以測試驗證） | ADR-0016、ADR-0019 |
| 預留組織層 | 新增組織表與活動上可為空的組織欄位；目前只有一個組織，不做任何介面 | ADR-0016 |
| 開放 Host 角色 | `add-role` 接受 Host；權限表與快照依 `api.md` 第 4、5 節追加 | `api.md` 第 4 節 |
| 平移 API | 平移試算（不寫入）與平移套用兩個端點，共用 `domain.PlanShift`；寫入帶版本號 | `tech-stack.md` 2.1「平移預覽」 |
| 快照追加 | Master 快照加超時分鐘；角色快照加變更提示；Host 的彙總快照 | `sync-and-offline.md` 第 2 節 |

**需要審查的部分**（`process/development-process.md` 第 5 節）：

- **Token 權限與資料外洩**：Host 快照內容、平移端點的權限、`guardAs` 修正。實作前 `security-reviewer` 一次，完成後 `verifier` 一次。
- **資料不遺失**：重建 `roles` 表的遷移、組織層的遷移。同上。

## 第一次真人彩排

M2a 的完成條件之一。以下情境條件在彩排中判定：

- 本文件所有 `.C` 條件。
- `stories/m1.md` 移過來的條件：US-M-3.C1、US-ST-1.C1、US-ST-1.C2、US-X-1.C1、US-M-0.C1。
- `product/vision.md` 第 7 節的兩個假設：
  - 至少一位**真正的廠商**（不只是親友扮演）用自己的手機參加，觀察是否需要說明、是否會主動再看。
  - 總召由**第一次接觸系統的人**擔任。

彩排的 Rundown、角色與參加者由 PO 安排；彩排結果與調整寫回本文件。
