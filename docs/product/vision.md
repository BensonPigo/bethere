# 產品願景與原則 (Product Vision)

> PO 於 2026-10-22 確認。所有需求取捨與設計判斷以本文件為最上層依據；與其他文件衝突時，以本文件為準並修正該文件。

---

## 1. 我們在打造什麼

**一份所有人共用、即時更新的活動當天流程表。**

- **總召**手上有「遙控器」：掌握現在進行到哪、誰到了；按一下「推進」或「延後 10 分」，所有相關的人的時間自動更新。
- **廠商與工作人員**點開 LINE 收到的連結，就看到**只與自己有關**的下一件事與倒數；免註冊、免安裝。
- **新人**當天不用操作任何東西，只在想看時瞄一眼，知道一切順利。

第一個場景是婚禮；第一場是開發者本人的婚禮（2027-06-06）。

## 2. 要解決的問題

**活動當天的時程一定會跑掉，而「通知所有人」目前全靠總召的腿與電話。**

1. **骨牌效應**：一個環節延誤，後面的環節全都要挪，但每個人手上是過時的紙本。
2. **溝通成本集中在總召**：跑新娘房、打電話、喊對講機，只為確認人到了、時間改了。
3. **每個角色都很難看手機**：新秘雙手不空、攝影手機在口袋、總召單手拿平板邊走邊講話。資訊必須一眼看懂，或完全不用碰。
4. **環境差**：昏暗、吵雜、訊號不穩；斷線時不能變成一片空白。
5. **只有一次機會**：不能重來；系統壞掉時不能比沒有系統更糟。

## 3. 兩個同等重要的核心價值

| 價值 | 說明 | 對應 |
| --- | --- | --- |
| **同一份即時流程表** | 所有人看到同一份、知道現在進行到哪 | 推進、角色視圖、倒數 |
| **變動自動傳到每個人** | 總召平移時程後，相關的人不必被通知就看到新時間 | 時間平移、被動感知時程變更 |

任何里程碑的真人驗證，都必須同時驗證這兩個價值。

## 4. 產品原則

| # | 原則 | 具體要求 |
| --- | --- | --- |
| V1 | **總召零學習成本** | 總召人選未定，可能不是專業婚顧。第一次拿到連結的人，不經說明就能完成核心操作；主畫面只放最常用的動作，其他收進第二層；復原碼等維運機制不讓總召接觸 |
| V2 | **不改變廠商的工作習慣** | 無法控制廠商是否使用。在 LINE 內建瀏覽器中就能完整使用（連線時），不要求改用其他瀏覽器；廠商端只需要看，不需要操作；不打開連結的人仍有退路（總召口頭通知、紙本備援），系統價值不建立在「所有人都打開」上 |
| V3 | **新人不被打擾，但知道一切順利** | 新人畫面只有一個狀態（一切順利／延誤 N 分）與目前環節；不推播、不震動、不需要操作 |
| V4 | **壞掉時不比沒有更糟** | 離線快照、紙本備援、決定日（2027-04-15）與降級方案（紙本 + LINE 群組） |
| V5 | **為商業化留後路，但不提前建造** | 目前是個人 side project，未來可能發展為有商業模式、可被收購的產品。現在就處理「之後改很貴」的結構，功能等需要時再做（`adr/0016-extensibility-principles.md`） |

## 5. 它刻意不是什麼

- 不是婚前籌備工具（預算、合約、邀請）。
- 不是聊天工具；不取代 LINE 群組，只取代「在群組裡喊時間改了」。
- 第一版不處理賓客（名單、到場率、禮金）。

## 6. 成功的樣子

活動當天，總召按下「延後 10 分」，新娘房裡的新秘抬頭一看，倒數已經變了，**沒有人需要跑去敲門**；新人事後回想，時程沒有讓他們操心。

## 7. 待驗證的最大假設

| 假設 | 驗證方式 |
| --- | --- |
| 廠商願意點開連結並看它 | 搭婚禮籌備的見面（試妝、婚攝會議、場勘），請真正的廠商（不只是親友扮演）當場開連結，觀察是否需要說明、是否會主動再看；決定日前完成（ADR-0027） |
| 不熟悉的人也能當總召 | 每個里程碑的小型實測找一位第一次接觸的人當總召，以情境條件判定；M3 完整彩排再驗證一次 |
