# ADR-0024：外部監控伺服器與備份，告警在活動前改送備援操作者

- 狀態：已接受
- 日期：2026-10-22
- 對應：`operations/runbook.md` 第 2、3 節；`design/tech-stack.md` 第 3 節；ADR-0009、ADR-0012、ADR-0013；RISK-5

## 背景

runbook 程序 2 的啟動門檻是「服務中斷超過約 10 分鐘」，但系統沒有任何監控（不安裝 Ops Agent，也沒有外部探測）：

- 第一個發現問題的人會是總召，可是總召只看到「離線中」，分不出是會場網路還是伺服器出問題，也不知道要不要找備援操作者。
- Litestream 若停止複製（權限、GCS 錯誤），沒有人會知道；VM 故障還原時才發現資料是舊的。
- 婚禮當天開發者是新人，不能當告警的接收者。

## 決定

- **伺服器探測**：以 Cloud Monitoring 的 Uptime Check 從外部探測 `/healthz`（`/healthz` 的行為不變，維護模式下仍正常，ADR-0012），連續失敗即告警。
- **備份新鮮度**：另提供一個端點（例如 `/healthz/replica`），在「本機已有變動、但超過 5 分鐘還沒複製到 GCS」時回失敗，由第二個 Uptime Check 探測。判斷依據是「尚未複製的變動」，不是「最後一個備份物件的時間」，因為資料庫閒置時本來就沒有東西可以複製。
  - Litestream 能否可靠提供這個資訊，在 M3 先以小型實驗確認；做不到時不做這個端點，改以 runbook 第 3 節「活動前一天實際還原一次」為唯一的檢查。
- **告警對象**：平時以 email 通知開發者；凍結期開始時（活動前 7 天）改為**只通知備援操作者**，以 Google Cloud 手機 App 推播加簡訊。切換寫進凍結期的檢查清單，婚後收尾時改回。
- **現場判斷**：紙本手冊寫明，總召看到「離線中」時先用自己的行動網路開一次連結；仍然離線就打給備援操作者。

## 考慮過的選項

| 選項 | 優點 | 缺點 |
| --- | --- | --- |
| Uptime Check + 備份新鮮度端點（採用） | 不需在 VM 安裝代理程式；故障與備份停擺都有人收到通知 | 多一個端點；告警管道要在凍結期切換 |
| 安裝 Ops Agent 收集指標 | 指標完整 | e2-micro 記憶體只有 1 GB；多一個常駐程式 |
| 不監控，靠總召回報 | 零成本 | 總召分不出網路與伺服器故障；備份停擺無人知道 |

## 後果

- 好處：程序 2 的啟動條件有客觀依據；備份停擺能在故障前被發現。
- 代價：Cloud Monitoring 的探測與簡訊可能產生少量費用（實作時以官方計價確認）；凍結期與婚後各多一個切換步驟。
- 之後要注意：
  - 演練時實際觸發一次告警，確認備援操作者的手機收得到。
  - 備份新鮮度端點不得透露活動資料，只回成功或失敗。
