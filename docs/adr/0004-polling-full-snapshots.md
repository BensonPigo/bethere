# ADR-0004：同步採每 2 秒輪詢完整快照，不用推送

- 狀態：已接受
- 日期：2026-10-20
- 對應：`sync-and-offline.md` S1、S2、S3；需求 E1、E2、E4、E7

## 背景

需求是總召操作後，95% 的終端在 3 秒內更新（E2）。單場最多 50 台裝置（E1）。現場網路不穩：地下室宴會廳、會場 Wi-Fi、手機切到背景後 iOS 會暫停連線。一個 Cue 清單只有數十筆。

## 決定

- 客戶端以**固定間隔每 2 秒**輪詢；上一次還沒完成就跳過這一輪；單次超過 8 秒算失敗。
- 伺服器每次都回該角色可見的**完整快照**（含 `serverTime`），不回差異。
- 總召的寫入走一般 API 請求，回應直接附上新快照。
- 客戶端用 `serverTime` 計算時鐘偏差（取最近數次的中位數），倒數在本機每秒重繪。

## 考慮過的選項

| 選項 | 優點 | 缺點 |
| --- | --- | --- |
| 固定間隔輪詢完整快照（採用） | 沒有連線狀態；漏掉一次，下一次就補齊；斷線重連就是「下一次輪詢」 | 平均延遲約 1 秒；請求量固定（50 台約每秒 25 個） |
| 推送為主（SSE／WebSocket），斷線退回輪詢（原設計） | 延遲最低 | 要處理推送連線的驗證、斷線重連、降級兩套路徑；iOS 背景會斷 |
| 輪詢差異（帶版本號只回變更） | 流量較小 | 要處理漏版、重組狀態；快照本來就很小，省不了多少 |

## 後果

- 好處：讀取路徑只有一條，撤銷 Token 在下一次輪詢（約 2 秒內）就生效；離線恢復不需要特別處理。
- 代價：延遲預算剛好 3 秒、沒有緩衝（寫入 400 ms + 等待 ≤ 2 秒 + 往返與重繪 600 ms）。
- 之後要注意：實測達不到時，先把間隔調到 1～1.5 秒。iOS 實測往返中位數 15～77 ms（`tech-stack.md` 5.1），目前預算足夠。
