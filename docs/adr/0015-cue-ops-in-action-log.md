# ADR-0015：Cue 操作以前後狀態記在 ActionLog，取代 ShiftLog

- 狀態：已接受
- 日期：2026-10-21
- 對應：`data-model.md` 4.1、ActionLog；ADR-0019；修訂 ADR-0006 的儲存方式

## 背景

ADR-0006 讓平移以 `ShiftLog`／`ShiftLogEntry` 記錄套用量，復原時反向扣回。但「復原上一步」不只復原平移：推進要還原兩個 Cue 的狀態與實際時間，略過要回到待辦。若只有平移有專用表，推進與略過的復原需要另一套紀錄，而且「最近一步」要跨兩種紀錄比較先後。

## 決定

- 推進、略過、平移都產生同一種 `domain.Op`：每個被改到的 Cue 在操作前後的狀態。
- Op 以 JSON 寫進 ActionLog 的 `payload`，`type` 為 `cue.<種類>`；被復原時填 `undoneAt`。payload 是 store 自己定義的格式（固定 JSON 鍵、帶版本號 `v`；操作種類只存在 `type`，不在 payload 重複），**只含 Op 會改的欄位**（狀態、偏移、實際時間），平移另含總召的要求（起點、平移量、取消勾選的 Cue）；不含標題等可編輯文字，Go 欄位改名也不會改變格式。
- 「復原上一步」= 最近一筆 `type` 以 `cue.` 開頭的紀錄；已復原過就不能再復原。其他動作（重發連結等）不算步驟。
- 最近一筆的種類或版本 `v` 看不懂、內容無法解析或為空時，**拒絕復原**，不會跳過它去復原更早的一步。未知的選填欄位會被忽略（與下方「只新增選填資訊時版本可以不變」一致）；不合法的狀態值寫回時由資料表的 CHECK 擋下。
- 平移要求在記錄前先整理：取消勾選的 Cue 只留本場存在的、去重；單次平移量上限 ±1440 分鐘。
- 資料庫以部分唯一索引保證同一場活動最多一個進行中的 Cue（`data-model.md` 4.1）；寫入時先寫離開進行中的 Cue。
- 復原前檢查這些 Cue 仍是操作後的狀態，不是就拒絕；只還原 Op 擁有的欄位（狀態、偏移、實際時間），現場改過的標題保留。
- 不建 `ShiftLog`／`ShiftLogEntry` 表。

## 考慮過的選項

| 選項 | 優點 | 缺點 |
| --- | --- | --- |
| 統一的 Op 記在 ActionLog（採用） | 一種紀錄、一種復原邏輯；最近一步只看一張表 | payload 是 JSON，SQL 無法直接查平移量 |
| ShiftLog 表 + 推進與略過另記 | 平移量可直接查詢 | 兩套復原邏輯；「最近一步」要跨表比較 |
| 每種操作各自一張表 | 結構最明確 | 表多、復原分支多，對單場活動沒有必要 |

## 後果

- 好處：`internal/domain` 的 `Undo` 一個函式涵蓋三種操作；資料庫少兩張表。
- 代價：要查某次平移的量，得解析 payload（前後 `offsetMin` 之差）。事後匯出在 Go 裡處理，不受影響。
- 之後要注意（發行版回退，ADR-0019）：
  - 新增操作種類時，`type` 一律用 `cue.` 開頭，舊版才會停在它前面而不是跳過它。
  - 新增「操作會改的欄位」時，payload 版本 `v` 要加一，舊版看到不認得的版本就拒絕復原。
  - 只新增選填的資訊（不影響還原）時，版本可以不變。

## 抗辯

2026-10-21 第一輪：三方皆 SURVIVED。依 red-team 與 skeptic 的意見補上固定格式、只存狀態欄位、版本號、未知操作拒絕復原、平移要求與唯一索引（見上方決定）。

2026-10-21 第二輪：三方皆 SURVIVED（連續兩輪無推翻理由）。依意見改為種類只存在 `type`、整理平移要求並限制平移量。曾加上「拒絕未知欄位」，第三輪 simplifier 指出它與「只新增選填資訊時版本可以不變」的規則矛盾，已移除，以版本號 `v` 為唯一契約。
