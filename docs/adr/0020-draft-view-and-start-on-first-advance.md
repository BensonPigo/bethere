# ADR-0020：Draft 階段照常顯示角色的 Cue，第一次推進即開始活動

- 狀態：已接受
- 日期：2026-10-22
- 對應：`design/screen-design.md` 3.4、4、5、6、9；`design/data-model.md` Event、4.1；`design/access-control.md` 第 4 節；`design/api.md` 3、4、5.6；`product/vision.md` V1、V4

## 背景

2026-10-22 的架構審查發現兩處與 V1、V4 衝突的設計：

- `api.md` 5.6 讓非 Master 角色在 Draft 階段也拿到完整快照，目的是讓裝置在活動前存好離線快照（`operations/runbook.md` 第 3 節）。但 `screen-design.md` 規定活動尚未開始時「一律」只顯示「活動尚未開始」。新秘若從早上就在訊號差的新娘房，裝置一直沒收到 Live 的快照，畫面會整天停在「尚未開始」，離線快照等於沒用。
- 「開始活動」是推進之外的另一個步驟。總召人選未定、可能是第一次使用（V1）；忘了按的話，全場都停在「尚未開始」。

## 決定

- **非 Master 角色在 Draft 階段照常顯示自己的 Cue**，「活動尚未開始」只是共通狀態層的一條窄條，不取代畫面：
  - 活動日當天：與 Live 相同，顯示「下一個與你有關的 Cue」與倒數。
  - 活動日以前：顯示自己的 Cue 清單與表定時間，不顯示倒數；窄條寫「活動尚未開始（M/D）」。
- **拿掉獨立的「開始活動」**：活動日當天（依活動時區），Draft 狀態下總召第一次按「推進」，在同一筆交易內把活動改為 Live 並開始第一個 Cue。非活動日按推進，照樣以 `not_event_day` 拒絕。
- 「復原上一步」只復原這次推進對 Cue 的改變，活動維持 Live，不回到 Draft。
- M1 已驗收的「開始活動」故事（`requirements/stories/m1.md` US-M-3.1）與 `POST /api/event/start` 於 M2a 改為上述行為；已驗收的故事不改寫，M2a 的故事另寫新的驗收條件。

## 考慮過的選項

| 選項 | 優點 | 缺點 |
| --- | --- | --- |
| Draft 照常顯示 Cue、第一次推進即開始（採用） | 離線快照在當天一定派得上用場；總召少一個步驟，不可能「忘了開始」 | 活動日當天推進前的 Rundown 結構編輯沒有明顯的「鎖定」時間點 |
| 維持「尚未開始」整頁畫面，另加提醒總召開始 | 狀態最清楚 | 離線時仍然停在「尚未開始」；提醒本身要總召注意到 |
| 到表定時間自動開始 | 不需要任何人操作 | 實際開始時間常與表定不同；伺服器自行改狀態，與「只有 Master 可異動」不一致 |

## 後果

- 好處：V4 的離線承諾在活動當天早上也成立；V1 的核心操作只剩「推進、延後、復原」。
- 代價：M1 已實作的開始活動端點與按鈕要在 M2a 調整；ActionLog 在第一次推進時多一筆活動開始的紀錄。
- 之後要注意：
  - 活動日當天、推進之前，總召仍可做 Draft 的完整編輯；第一次推進後才轉為 Live 的限縮編輯。
  - 推進一律帶版本號，所以兩台總召裝置同時按第一次推進時，只有一台會成功。
