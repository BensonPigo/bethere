# ADR-0029：端對端測試路線在 VM 的測試服務上，由 PO 手動執行

- 狀態：已接受
- 日期：2026-10-22
- 對應：`process/e2e-test-routes.md`；`process/development-process.md` 第 1、4 節；ADR-0009、ADR-0027

## 背景

M2b 的真機自測有五條情境條件，其中「斷網時仍看得到時程」「伺服器停擺後自己恢復」「點了按鈕畫面有沒有跟著變」屬於功能是否正確，不需要人判斷，卻只能靠 PO 在真機上一項項看。每個里程碑都這樣做，PO 的時間會被花在機器能做的事上。

限制：

- 只有一台 VM（ADR-0009），M3 之後婚禮的真實資料也在上面。
- 推進只能在活動日當天按，所以每次測試都要建一場日期是今天的活動；建立活動只能在伺服器上用指令（`access-control.md` 第 2 節）。
- CI 的免費分鐘數有限（`process/development-process.md` 第 6 節）；把 GCP 金鑰放進 GitHub 會多一個權限外流的途徑。

## 決定

- 以 Playwright 寫**測試路線**：用 Safari 的引擎（WebKit），模擬總召的 iPad 與其他角色的 iPhone，照使用者的實際操作點按鈕、看畫面。路線的清單在 `process/e2e-test-routes.md`。
- 在**同一台 VM 上另開一個測試服務**（`bethere-e2e`）：同一個發行版、**自己的資料庫**（`/var/lib/bethere-e2e/e2e.db`）與埠號，以獨立的網域經 Caddy 對外。每次執行都重建這個資料庫；伺服器停擺的路線只停這個服務。正式服務與資料庫一律不碰。
- **PO 在自己的 Mac 上手動執行**（`npm run e2e`），用已登入的 `gcloud` 建立測試活動、停止與啟動測試服務；不放進 CI，不把金鑰交給 GitHub。
- 同一套路線也能在本機對從原始碼建置的服務執行，開發時先跑過再部署。
- 路線只驗功能是否正確；情境條件（`US-x-n.Cm`）仍由 PO 或真實使用者在真機上判定。

## 考慮過的選項

| 選項 | 優點 | 缺點 |
| --- | --- | --- |
| 同一台 VM、另開測試服務，PO 在 Mac 上執行（採用） | 走的是真正的網路、Caddy 與 HTTPS；不多花錢；與正式資料分開 | VM 多一個服務；Caddy 設定多一個網域 |
| 直接用正式服務 | 最簡單 | M3 之後測試活動與婚禮資料在同一個資料庫；停擺路線會真的停掉正式服務 |
| 另開一台測試 VM | 完全隔離 | 每月多一台 VM 的費用，部署要做兩次 |
| GitHub Actions 手動觸發 | 不用開電腦 | GCP 金鑰要放進 GitHub；用掉 CI 分鐘數 |
| 只在本機跑 | 不動 VM | 驗不到真正的網路、Caddy、HTTPS 與部署後的版本 |

## 後果

- 好處：每次部署後幾分鐘就能確認全部路線；PO 的真機時間只花在「人用起來順不順」。
- 代價：
  - 測試服務對外可連，但只有測試資料，連結是每次重建的隨機 Token。
  - 第一次設定（`ops/gcp/e2e-setup.sh`）會讓 Caddy 重啟一次，約一秒。
  - 模擬瀏覽器不等於真機：iOS 的螢幕常亮、LINE 內建瀏覽器、Service Worker 的實際行為仍要真機確認。
- 之後要注意：
  - 換成正式網域時（RISK-6），測試服務的網域（預設 `e2e.<正式網域>`）要另設 DNS 紀錄。
  - M3 加入備份（Litestream）時，只備份正式資料庫，不含 `/var/lib/bethere-e2e`。
  - 凍結期（活動前 7 天）與活動當天不執行測試路線。
