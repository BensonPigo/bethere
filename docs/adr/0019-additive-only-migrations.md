# ADR-0019：資料庫遷移只做向後相容的新增

- 狀態：已接受
- 日期：2026-10-22
- 對應：`design/tech-stack.md` 2.1「SQL 與遷移」；ADR-0015、ADR-0016

## 背景

這條規則在 `tech-stack.md`（原 T4）訂定，ADR-0015、ADR-0016 與 `process/development-process.md` 第 9 節都依賴它，但沒有自己的 ADR。

部署出問題時，回退方式是換回上一個發行版（ADR-0009），資料庫不跟著回退。舊版程式必須能直接打開新版遷移過的資料庫，否則回退會失敗，而回退通常發生在最需要它的時候（活動當天或前幾天）。

SQLite 不能修改既有欄位的 CHECK 限制，只能重建整張表。`roles.type` 目前以 CHECK 寫死婚禮的角色類型，M2a 要改為在 Go 驗證（ADR-0016），必須重建 `roles` 表。

## 決定

- 遷移只做向後相容的新增：加表、加可為空的欄位、加索引。
- 已發行的遷移檔不再修改；結構變更一律新增編號遷移檔，以 `PRAGMA user_version` 記錄版本。
- 程式遇到比自己新的 `user_version` 照常啟動，不嘗試降級。
- **唯一的例外**：正式環境放入真實資料之前，可以用重建表的方式修改限制（目前只有移除 `roles.type` 的 CHECK）。重建的遷移同樣以新增檔案的方式發行；正式資料出現後，例外失效。

## 考慮過的選項

| 選項 | 優點 | 缺點 |
| --- | --- | --- |
| 只做向後相容的新增，正式資料前允許一次重建（採用） | 回退只需要換執行檔；舊版能讀新庫 | 欄位不能改名或改型別；錯誤的結構只能以新增修補 |
| 每個遷移都附降級腳本 | 結構可以自由修改 | 降級腳本平常不會執行，最需要時最可能出錯；回退要多一個步驟 |
| 完全不允許例外 | 規則最簡單 | 角色類型的 CHECK 會永遠擋住新的角色類型（ADR-0016） |

## 後果

- 好處：回退發行版不需要碰資料庫；活動當天的回退步驟最少。
- 代價：結構累積「只增不減」的欄位；欄位設計要一開始就想清楚。
- 之後要注意：
  - 移除 `roles.type` 的 CHECK 必須在正式資料出現前完成（M2a；最遲 M3 前）。
  - Cue 操作紀錄的格式演進另依 ADR-0015 的版本號規則。
