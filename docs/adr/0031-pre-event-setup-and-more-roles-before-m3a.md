# ADR-0031：M3a 之前先做婚前準備（M2c）與更多角色（M2d）

- 狀態：已接受
- 日期：2026-10-24
- 對應：`requirements/scope.md` 第 2 節；`product/vision.md` 第 5 節；`process/development-process.md` 第 3 節；ADR-0030

## 背景

M2b 驗收後盤點產品面：活動當天的功能已大致齊全，但婚禮前的準備全部要由開發者在 VM 上下指令：

- 加角色、匯入 Rundown 都靠指令；Rundown 只能匯入一次（`stories/m1.md` US-M-0.2a）。
- 改既有 Cue 的時間、長度、順序，或刪除 Cue，只能重建活動，所有連結都要重發。
- `screen-design.md` 第 6、7 節設計了 Rundown 編輯器與角色與連結管理，`access-control.md` 第 4 節的權限表也允許 Master 在 Draft 編輯 Rundown，但兩者都沒有排進任何里程碑。

現場角色方面，`requirements/roles-and-scenarios.md` 的主持、領班、機動組、迎賓、禮金都還沒有畫面；領班雙向確認與機動組任務池是 P1，賓客相關是 P2，`product/vision.md` 第 5 節寫明「第一版不處理賓客」。

時程上，M2b 比目標（2027-01 底）提早約三個月完成。

## 決定

PO 決定在 M3a 之前插入兩個里程碑，都列為 P0：

- **M2c 婚前準備**：Draft 階段的 Rundown 編輯器（改時間、長度、固定、順序、刪除、指派與角色備註）；總召在畫面上新增角色（自取名稱、選畫面、選要不要打卡）與產生連結；貼上 CSV 匯入；連結的 QR Code；以某角色預覽。建立活動仍由開發者以指令執行（ADR-0016）。
- **M2d 更多角色**：主持、領班（含雙向確認）、機動組（含任務池）、迎賓與禮金（含賓客名單）。

「總召在畫面上新增角色」只讓總召選名稱、畫面與是否打卡，對應到既有的角色類型；權限仍由類型決定，不做可設定的權限表。

第一版**處理賓客**，推翻 `product/vision.md` 第 5 節的「第一版不處理賓客（名單、到場率、禮金）」。賓客名單的存取範圍、蒐集欄位與刪除，在 M2d 的故事與設計中定案；刪除承諾（NFR-5）同樣適用。

M2d 的故事依 `process/development-process.md` 第 3 節，在 M2c 接近完成時才寫；屆時依剩下的時間決定 M2d 的內容。

## 考慮過的選項

| 選項 | 優點 | 缺點 |
| --- | --- | --- |
| M3a 前插入 M2c、M2d（採用） | 婚前準備不必靠開發者；有時程空間 | 正式的婚禮資料要等 M3a 的備份與維護模式完成才能輸入（RISK-9） |
| 先做 M3a，再補功能 | 先消除資料遺失的風險 | 準備功能延後，婚前改流程表仍要重建活動 |
| 婚前準備與角色合成一個里程碑 | 少一次驗收 | 範圍大，中間沒有驗收點；角色的份量不確定 |
| 總召可設定新角色的權限 | 彈性最大 | 權限表變成資料，Token 權限邊界的審查與測試大幅增加 |

## 後果

- 好處：總召可以自己維護流程表與角色，婚前改流程不必重建活動或重發連結。
- 代價：
  - M3a、M3b 往後移，時程空間大致用完；M2d 是否全部做完，到時依剩下的時間決定。
  - 賓客名單是賓客的個人資料，是新的資料外洩面。
- 之後要注意：
  - M2c 開放 Draft 階段的結構性編輯，與活動日當天第一次推進（ADR-0020）、平移、復原上一步的互動要在 `api.md` 寫清楚。
  - M3a 完成前，正式環境仍只放測試活動（RISK-9）。
