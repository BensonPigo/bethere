# ADR-0001：以 ADR 記錄架構決策

- 狀態：已接受
- 日期：2026-10-21
- 對應：—

## 背景

BeThere 由一人開發，第一場使用是開發者自己的婚禮（2027/06/06）。設計階段已做過多輪三方抗辯審查，許多決定是推翻原案後才定下來的，例如 Owner 併入 Master、推送改為輪詢、Fly.io 改為 GCE。這些「為什麼不選另一個」的理由目前散在各設計文件的決定表與 git 歷史裡，半年後回頭看或交接給備援操作者時很難找回來。

## 決定

架構層級的決定以 ADR 記錄在 `docs/adr/`，格式見 `0000-template.md`。設計文件繼續作為實作細節的依據，ADR 只記錄背景、選項、取捨與後果。

判斷是否需要 ADR：改了會牽動多份設計文件、多個元件或部署方式，或是推翻了先前的決定。單一畫面的互動細節（U 系列）不寫 ADR。

## 考慮過的選項

| 選項 | 優點 | 缺點 |
| --- | --- | --- |
| 獨立的 ADR 檔（採用） | 每個決定的理由與被否決的選項集中在一處；推翻時留下歷史 | 與設計文件有少量重複 |
| 只用設計文件裡的決定表 | 不重複 | 表格只有一行結論，裝不下被否決的選項與後果 |
| 只靠 git commit message | 零成本 | 找不到，也無法一次看完全部 |

## 後果

- 好處：重大決定的理由可追溯，推翻時不會忘記原本為什麼這樣選。
- 代價：新增或推翻決定時要同時更新 ADR 與設計文件。
- 之後要注意：ADR 接受後不改寫內容；只更新「狀態」一行。
