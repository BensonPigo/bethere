# ADR-0030：M3 拆成資料與維運（M3a）、現場準備（M3b）

- 狀態：已接受
- 日期：2026-10-23
- 對應：`process/development-process.md` 第 3 節；`requirements/scope.md` 第 2 節；ADR-0027

## 背景

M3 原本列了九項：維護模式、每日刪除、`reset-recovery-code` 指令、備援 Rundown 列印、當天維運腳本與演練、外部監控與告警、Android 實機、負載測試、建立活動寫進 runbook。盤點程式碼後發現，其中幾項依賴兩件尚未實作的事：

- **持續備份（Litestream）**：ADR-0009 與 `design/tech-stack.md` 第 3 節已決定，但 VM 上沒有安裝；磁碟故障時資料全部遺失。維護模式與故障重建都以「能從備份還原」為前提。
- **復原碼入口**：`create-event` 會印出復原碼，儲存層也支援，但沒有 `/recover` 的 API 與畫面；維護模式要放行的「換發 Master」也還不存在。

加上這兩項後，M3 的工作量約等於 M2a 與 M2b 的總和，而且大多落在「資料不遺失」與「當天維運」兩個風險邊界（`process/development-process.md` 第 5 節）。

## 決定

M3 拆成兩個里程碑，各自驗收：

- **M3a 資料與維運**：持續備份與開機還原、維護模式、復原碼入口、`reset-recovery-code`、每日刪除、當天維運腳本與在暫存專案的演練、外部監控與告警。
- **M3b 現場準備**：備援 Rundown 列印、Android 實機、負載測試、建立活動的步驟寫進 runbook（US-M-0.C1）、正式網域，以及唯一一次的完整彩排（ADR-0027）。

持續備份與復原碼入口明列為 M3a 的範圍（P0）。風險高、其他項目依賴的先做。

備援操作者尚未決定，M3a 的演練先以 PO 的帳號在暫存專案進行；人選決定後，由他本人以自己的帳號與筆電再演練一次（`operations/runbook.md` 第 2 節）。

## 考慮過的選項

| 選項 | 優點 | 缺點 |
| --- | --- | --- |
| 拆成 M3a、M3b（採用） | 資料與維運先完成並驗收；完整彩排時備份與故障重建已經可用 | 多一次驗收 |
| 不拆 | 少一次驗收 | 中間沒有驗收點，備份或維運的問題要到最後才發現 |

## 後果

- 好處：完整彩排在 M3b，彩排當天就有備份、維護模式與故障重建可用。
- 代價：里程碑表、範圍表與代號表都要改為 M3a、M3b。
- 之後要注意：
  - ADR-0027 的「完整彩排在 M3」指 M3b。
  - 演練以 PO 的帳號進行，只證明腳本可行，不證明備援操作者的權限足夠；本人演練前，RISK-5 不能結案。
