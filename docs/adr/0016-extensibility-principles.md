# ADR-0016：為商業化留後路的擴充性原則

- 狀態：已接受
- 日期：2026-10-22
- 對應：`product/vision.md` V5；`archive/clarification.md` C4

## 背景

BeThere 目前是個人 side project，第一個目標是 2027-06-06 的婚禮；PO 表示未來可能發展為有商業模式、可被收購的產品（例如給婚顧公司使用），希望設計時就考慮擴充性。

同時，時程只有約 7 個月、一人開發，過早建造多租戶、帳號、計費等功能會拖垮第一個目標。需要一個判斷標準，決定哪些現在做、哪些只留後路。

已知會成為障礙的地方（2026-10-21 外部診斷）：
- 角色類型以資料庫 CHECK 限制寫死為婚禮角色，而遷移規則只允許新增（ADR-0019），SQLite 修改 CHECK 需要重建整張表。
- 活動直接是最上層的實體，沒有「組織／帳號」層。
- 只有一個 Master，活動只能由開發者以指令建立。
- 輪詢每次回完整快照，多場活動同時進行時流量會放大。

## 決定

以「**改的成本**」區分：

1. **現在就處理**：正式環境放入真實資料後就很難改的結構。
   - 角色類型改為在 Go 驗證，資料庫只存文字（M2；需要新遷移，以重建表的方式移除 CHECK，必須在正式資料出現前完成）。
   - 在資料模型預留「組織」層：活動屬於某個組織；目前只有一個組織，不做任何介面（M2 一併評估，以新增表與可為空的欄位完成，符合 ADR-0019）。
2. **只留後路，不建造**：
   - API 與 store 不假設「一個活動只有一個管理者」；權限以角色類型與 capability 判斷，不以「是不是那個唯一的 Master」判斷。
   - 建立活動的邏輯放在 store／服務層，指令只是其中一個呼叫端；之後加自助建立只需要新增 API 與畫面。
   - 介面文字集中管理，不散落在元件中。
   - 快照端點支援以版本號回 304（M2）。
3. **刻意不做**：帳號與登入、計費、多語系內容、WebSocket、Postgres、容器化、多區域部署。

判斷新項目時問兩個問題：「正式資料出現後還能便宜地改嗎？」「現在做會延誤 2027-06-06 嗎？」前者為否才現在做；後者為是就只留後路。

## 考慮過的選項

| 選項 | 優點 | 缺點 |
| --- | --- | --- |
| 依改的成本區分，只處理難改的結構（採用） | 不延誤婚禮；收購時的主要結構障礙已移除 | 之後仍需要開發多租戶與帳號功能 |
| 現在就做多租戶、帳號、自助建立 | 商業化時立即可用 | 數週到數月的工作量，直接威脅 2027-06-06 |
| 完全不考慮，等商業化再說 | 最快 | 正式資料出現後，角色類型與組織層的修改需要資料遷移 |

## 後果

- 好處：第一個目標不受影響；商業化時不需要重寫資料層。
- 代價：M2 多出兩項結構調整（角色類型、組織層）。
- 之後要注意：
  - 新的設計若引入「只有婚禮才有」的假設（固定的角色清單、固定的活動結構），應改為資料或設定。
  - 被收購時會檢查程式碼的權利歸屬；開發環境與權利歸屬由 PO 自行確認（不在本 ADR 範圍）。
