# ADR-0033：收斂到最小可用版本：先做備份，新功能暫停，人工試用只在最後做一次

- 狀態：已接受
- 日期：2026-10-24
- 對應：`process/development-process.md` 第 3 節；`requirements/scope.md` 第 2 節；`requirements/stories/m3a.md` US-O-1；ADR-0027、ADR-0031

## 背景

專案 2026-10-20 開始，四天內驗收了 M1～M2c，文件約 5,100 行、程式約 17,000 行。PO 表示系統大到看不太懂，也不確定需求是否形成閉環，希望以最小可行產品為優先、只在關鍵點把關，人工測試與驗收減到最少並放到最後。

盤點「一場婚禮從頭到尾」：建立活動（開發者下指令）、婚前準備、傳連結、當天推進與平移、各角色看倒數，功能都已完成；唯一缺的是**資料備份**，主機或磁碟壞掉時流程表會消失。

## 決定

PO 決定：

- **先做持續備份與開機還原**（`stories/m3a.md` US-O-1）。
- **其他新功能暫停**，包括 M2d 全部（主持、領班、機動組、迎賓與禮金）。M3a 其餘項目與 M3b 的內容，等備份完成後再依「最小可用」重新決定。
- **中間不再做小型實測**；驗證以自動測試與 AI 代理自行執行的演練為主，人工試用只在最後做一次（PO 與幾位親友），取代 ADR-0027 的「每個里程碑一次小型實測」。完整彩排仍只做一次，且在決定日（2027-04-15）之前。

## 考慮過的選項

| 選項 | 優點 | 缺點 |
| --- | --- | --- |
| 先做備份，其他暫停（採用） | 補上唯一會讓系統比紙本更糟的缺口；範圍小、PO 容易掌握 | 主持、領班、賓客等角色第一場可能沒有專屬畫面 |
| 照原計畫做 M2d | 角色更完整 | 範圍繼續擴大；正式資料仍沒有備份 |
| 每個里程碑繼續小型實測 | 及早發現不好用的地方 | 佔用 PO 時間，與 PO 的期望不符 |

## 後果

- 好處：PO 只需要在少數關鍵點把關；系統有了資料不遺失的保證後，才放真實資料。
- 代價：「好不好用」的問題會較晚才發現；廠商是否願意打開連結（`product/vision.md` 第 7 節）仍只能由真人回答。
- 之後要注意：最後一次人工試用要排在決定日前、留出修改的時間；ADR-0031 中 M2d 與「第一版處理賓客」暫不執行，恢復時再決定。
